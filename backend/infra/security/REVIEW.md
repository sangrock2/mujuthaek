# 보안 검토 기록 — 2026-11-16

이 기록은 확인한 코드·운영 정책, 수정한 항목, 남은 검증을 구분합니다. 전체 시스템에 취약점이 없다는 보증이나 침해 사고 확인 결과가 아닙니다. 실제 사용자 토큰·데이터로 공격하지 않고 회귀 검사는 격리된 테스트 DB에서 수행합니다.

## 1. 로그아웃 뒤 회전 전 토큰으로 세션을 재발급할 수 있는 경로

발견 근거: 기존 `AuthTokenService.refresh()`는 회전 전 토큰을 30초 동안 허용하지만 `revoke()`는 전달된 토큰 한 개만 삭제했습니다. T0 → T1 회전 후 T1으로 로그아웃해도 T0가 남아 유예 시간에 다시 토큰을 받을 수 있었습니다. 공격자는 유효한 토큰 사본을 가지고 있어야 하며, 이것만으로 임의 계정에 로그인할 수 있다는 의미는 아닙니다.

변경: 로그인별 `family_id`를 두고 회전한 토큰과 동시 요청에서 파생된 토큰을 같은 계보로 연결합니다. 로그아웃은 해당 계보를 모두 삭제합니다. 사용자 행 잠금 후 토큰과 현재 시각을 다시 확인해 로그아웃과 재발급 사이의 경합을 직렬화합니다. 별도 로그인에서 발급한 토큰은 유지합니다.

검증: `SecurityIntegrationTest.logoutRevokesRotatedTokenAndKeepsAnotherLogin`과 `racingLogoutAndRefreshCannotLeaveARefreshSessionAlive`. `Security regression proof` 워크플로는 고정한 과거 커밋의 전체 소스를 임시 폴더에 복원하고 동일한 `HistoricalLogoutRegressionTest`를 실행합니다. 과거 버전이 정확히 **401을 기대했지만 200이 반환돼 실패**하고 현재 버전은 통과해야 합니다. 다른 컴파일·DB·네트워크 오류는 재현 성공으로 인정하지 않습니다. 증거는 `logout-security-proof` artifact의 XML·JSON·검사 파일 SHA에 보관합니다. [첫 실 DB 재현·수정 검증 성공](https://github.com/sangrock2/mujuthaek/actions/runs/43708973537/job/132796192485). 후속 변경의 CI와 운영 배포 상태는 별도로 확인합니다.

운영 영향: 새 컬럼·인덱스 마이그레이션이 있습니다. 기존 미회전 토큰의 로그인은 유지하고, 계보를 복원할 수 없는 이전 버전의 회전된 토큰은 유예를 종료합니다. 스키마 변경 후 앱만 과거 버전으로 되돌리는 작업은 기존 배포 보호 장치에 따라 제한됩니다. 1차 배포에서는 access token 즉시 폐기와 재사용 감지를 남겨 두었으며, 아래 후속 수정으로 보완합니다.

## 3. 개인 데이터 접근 권한

신청 준비함은 기존에도 사용자 ID를 사용해 소유권을 검사합니다. 기존 조회·상태 변경 검사에 HTTP 체크리스트 수정·삭제, 준비함 삭제, 다른 준비함의 작업 ID 혼합 검사를 보강했습니다. 체크리스트 수정·삭제는 404로 거부하고, 준비함 삭제는 없는 항목·남의 항목 모두 204로 조용히 무시하는 기존 계약을 유지합니다. 상태 코드만으로 성공 여부를 판단하지 않고 원래 소유자의 데이터가 바뀌지 않는지도 확인합니다. 기존 푸시 구독의 다른 사용자 기기 삭제 방지, 관리자 권한 회수 후 동일 JWT 거부 검사도 유지합니다. 문의·제보는 기존 내 제보 목록의 사용자별 분리 검사가 통과한 범위까지 확인했으며, 문의 전체 경로의 새 권한 검증을 마쳤다고 주장하지 않습니다. 취약점이 재현되지 않은 경로를 새로 발견·수정한 결함으로 표현하지 않습니다.

## 4. S3와 운영 권한 경계

운영 조회에서 이미 확인한 조치: 버킷의 공개 접근 차단 4개, 공개 ACL 부재, 비공개 정책 상태, 기본 암호화, 앱 IAM의 배포 경로 명시적 거부. 서버 방화벽의 전체 인터넷 공개 TCP 포트는 HTTP·HTTPS였으며 SSH 전체 공개는 확인되지 않았습니다.

1차 보완: 버킷에 명시적 HTTPS 강제 정책을 추가하고, 새 운영 보고·알림 중복 방지 경로를 앱 IAM에서 명시적으로 거부했습니다. 기존 배포 경로 거부도 유지합니다. AWS 서비스가 호출할 때 일부 네트워크 문맥이 생략되는 점을 고려해 서비스 주체는 전송 조건의 예외로 둡니다. 이 단계에서는 공개 접근 허용·새 자격 증명 생성·데이터 삭제를 하지 않았습니다.

1차 적용 후 IAM 시뮬레이션에서는 원문·백업 Get/Put이 허용되고 배포·운영 경로가 거부됐습니다. 이후 아래 후속 작업으로 백업 접근도 앱에서 분리했습니다. 예전에도 차단된 배포 경로를 이번에 처음 차단했다고 기록하지 않습니다. 서명 URL은 추가하지 않았고, 공고 PDF는 기존 공개 상태·파일 경로 검증 후 서버 스트리밍 구조를 유지합니다.

## 5. 후속 검토 항목

배포 공급망도 함께 보완했습니다. 외부 GitHub Actions 참조 39개를 공식 태그가 가리키는 커밋 SHA로 고정했고, 태그 주석을 유지해 Dependabot 업데이트를 검토할 수 있게 했습니다. 이는 이후 태그 변경에 따른 코드 교체를 방지하는 조치이며 해당 액션 내부 의존성까지 모두 고정했다는 의미는 아닙니다.

Gitleaks 8.30.1로 Git 이력을 검사한 원시 탐지는 5개였습니다. 3개는 테스트 실행 중 생성하는 RSA 키에 붙이는 PEM 구분자였고, 나머지는 Web Push RFC 시험 벡터와 입력값 비노출 검사의 모의 문자열이었습니다. 검토한 과거 커밋·경로·규칙·행의 정확한 fingerprint만 `.gitleaksignore`로 예외 처리합니다. 테스트 디렉터리나 커밋 전체를 제외하지 않습니다. 새로 생성한 가상 비밀값이 여전히 탐지되는 canary 검사와 checksum을 고정한 검사기를 필수 CI에 연결합니다. 검사 결과나 토큰 문자열은 공개 로그에 내보내지 않습니다. 이번 검사에서 실운영 키 유출은 확인되지 않았으며, 도구가 모든 형태의 비밀값을 탐지한다는 뜻은 아닙니다.

저장소의 GitHub Secret scanning과 Push protection도 활성화했습니다. 공급자에게 탐지 키를 보내는 validity checks는 활성화하지 않았습니다. 실키가 발견되면 파일에서 지우는 것에 앞서 해당 공급자에서 폐기·재발급해야 하며, Git 이력 변경은 별도로 검토합니다. Dependabot의 자동 보안 수정 PR은 기본 브랜치로만 향하므로 기존 dev → main 규칙과 충돌하지 않도록 이번에는 켜지 않았습니다. dev 대상 주간 버전 업데이트와 필수 취약점 CI를 사용합니다.

- Vercel → Nginx에서 실제 사용자 IP를 신뢰할 조건과 요청 제한 키 검증. 전달 헤더를 무조건 신뢰하도록 바꾸지 않습니다.
- 인증 쿠키 경로의 CORS·Origin·SameSite 조건을 실제 브라우저로 검증. 현재 CORS가 차단하는 요청을 CSRF 취약점으로 단정하지 않습니다.
- CSP는 지도·로그인·PDF·서비스 워커의 출처 목록과 보고 방식부터 설계합니다. 정책을 무조건 강제해 기능이 깨지게 하지 않습니다.
- 수집기의 사설 IP·DNS 고정·리다이렉트 차단과 푸시 도메인 허용 목록은 기존 방어입니다. 우회 사례·회귀 검사를 추가 검토합니다.
- 외부 문서 파서의 크기·시간·메모리 제한, AI 프롬프트 인젝션과 공개 승인 경계, 컨테이너 이미지·배포 작업의 공급망, Git 과거 이력의 비밀값을 별도 점검합니다.
- AWS 관리자의 root 로그인 사용을 줄이고 별도 관리자 역할·MFA 체계를 정하는 작업은 운영자 설정을 동반합니다.

## 6. 후속 수정과 검증 경계

### 로그인 토큰

사용자 승인에 따라 회전 전 토큰의 30초 유예를 제거했습니다. 사용한 해시는 원래 만료일까지 남겨 재사용을 감지하고 해당 로그인 계보를 삭제합니다. 다른 기기의 별도 로그인은 유지합니다. JWT에는 `sid`만 추가하고 원문 토큰은 인증 객체에 보관하지 않습니다. 인증된 읽기·쓰기 요청 모두 DB의 현재 세션·정지·탈퇴 상태를 확인해 로그아웃 이후 남은 JWT도 거부합니다. 이미 처리 중인 요청을 취소하는 기능은 아닙니다. 세션 없는 구 JWT는 401이며, 유효한 기존 refresh 쿠키로 새 JWT를 받을 수 있습니다.

발급은 사용자 행 잠금 안에서 계정별 분당 30개로 제한합니다. 제한에 걸린 정상 refresh 토큰은 소비하지 않습니다. Nginx의 IP 제한을 제거하거나 전달된 `X-Forwarded-For`를 신뢰하지 않습니다. Vercel 경유 요청은 같은 프록시 IP를 공유할 수 있으므로 기존 IP 제한은 사용자별 제한이라고 설명하면 안 됩니다.

브라우저의 기존 Web Locks 잠금을 로그아웃에도 적용하고, 완료된 로그아웃만 BroadcastChannel로 다른 탭에 알려 개인 캐시를 지웁니다. 토큰 값은 전송하지 않습니다. 지연된 재발급 응답이 로그아웃 상태를 되돌리지 않게 세대 번호를 확인합니다. 서버 연결 실패는 로그아웃 성공으로 표시하지 않습니다. Web Locks가 없는 브라우저 또는 회전 응답이 유실된 경우에는 재로그인이 필요할 수 있습니다. 보안상 옛 토큰의 자동 재시도는 하지 않습니다.

실 DB 검사는 재사용·동시 회전·로그아웃 경합·다른 로그인 보존·즉시 JWT 거부·기존 JWT 전환·계정별 제한을 포함합니다. Playwright 검사는 두 탭의 회전·로그아웃·개인 캐시 제거와 로그아웃 통신 실패를 포함합니다. 전체 CI 성공 전까지 브라우저·DB 검증 완료로 기록하지 않습니다.

### 백업 접근 분리 — 서버 적용 확인

승인받은 백업 전용 IAM 사용자와 액세스 키 하나를 만들었습니다. `backups/`의 읽기와 새 객체 쓰기만 허용하고, 쓰기는 IAM 조건에서 `If-None-Match: *`를 요구해 기존 객체 덮어쓰기를 거부합니다. 삭제·원문·운영·배포 권한은 없습니다. 앱은 `raw/`에 필요한 권한만 유지하고 `backups/` 객체 접근을 명시적으로 거부합니다.

기존 업로더가 실행할 때마다 앱 키로 백업 설정을 다시 쓰던 경로도 제거했습니다. 전용 설정이 없으면 실패하며 앱 키로 대체하지 않습니다. 자격 증명 파일은 Git에서 제외하고 로컬 소유자·서버 root만 읽도록 설정했습니다. 전환 시 실행 중 백업이 끝날 때까지 기다리고 타이머·파일 잠금으로 경합을 막습니다. 주체 확인, 합성 파일 업로드·다운로드·덮어쓰기 거부가 성공한 뒤에만 앱 권한을 줄입니다. 실제 DB 네 개의 백업 실행 성공과 IAM 허용·거부를 확인했고, 키 만료 점검 대상에도 연결했습니다. 백업 30일 보관 정책은 기존 승인대로 유지합니다.

초기 설치에도 별도 백업 주체를 준비해야 합니다. `backup_security.py prepare --config <비공개 운영 설정>` → owner 전용 파일을 `remote.py upload-private`로 전송 → 검토한 업로더·스크립트 SHA256을 인자로 `configure_backup_identity.py` 실행 → 반환된 주체·버킷·키 fingerprint 영수증으로 `backup_security.py finalize --config <설정> --receipt <영수증>` 순서입니다. 임의의 영수증·기존 미추적 키는 거부합니다. 키·환경 파일·SSH 결과 전체를 공개 로그에 남기지 않습니다. 장기 키의 주기적 교체 및 호스트 root 침해 위험은 남습니다. 권한 분리가 같은 호스트의 root까지 격리하는 것은 아닙니다.

### 문의·관리자와 웹 출처

현재 문의는 일반 제보와 관리자 답변 경로입니다. 회원용 비공개 문의 상세 수정 API가 별도로 존재한다고 가정하지 않습니다. 회원 및 REPORTS 권한 없는 관리자의 목록·건수·큐·상세·처리 시작·검수·답변 거부, 권한 부여·회수 직후 동일 JWT 처리, 일반 문의의 묶음 처리 격리, 내 목록에 타인의 답변이 섞이지 않는 검사를 추가했습니다. 현재까지 새 권한 우회가 재현된 것은 아니므로 검증 보강으로 분류합니다.

기존 CORS가 비신뢰 출처·허용 도메인과 닮은 출처·`null` 출처의 refresh/logout 요청을 거부하고 쿠키를 소비하지 않는지 검사합니다. CSP는 전역에 `object-src 'none'; base-uri 'self'; frame-ancestors 'none'`만 추가합니다. 지도·Next 스크립트를 막는 `script-src`는 이번에 도입하지 않았으므로 완전한 XSS 방어 CSP라고 표현하지 않습니다. React의 기존 텍스트 렌더링을 우회하는 raw HTML 삽입 경로는 이번 검색에서 확인되지 않았습니다.

### 외부 문서의 자원 증폭

확인한 누락: 수집기의 HWPX XML 압축 해제에는 별도 크기 제한이 없었습니다. 작은 ZIP도 큰 XML로 확장될 수 있어, 해제 전 전체 크기 50MiB·항목 수 2,048개를 검사하고 실제 읽기에도 남은 바이트 제한을 적용합니다. 초과 파일은 읽기 실패로 남기며 정상 추출처럼 AI에 보내지 않습니다.

엑셀에는 이미 해제 크기 50MiB 제한이 있었지만 병합 셀의 행 번호 범위를 그대로 반복했습니다. 작은 XML의 큰 범위만으로 많은 빈 행을 순회할 수 있었습니다. 이제 유효한 시트 좌표를 검사하고 저장한 행만 순회합니다. 큰 정상 병합은 실제 존재하는 행에만 반영하고 시트 밖 범위는 거부합니다. 두 경우 모두 네트워크·유료 AI 없이 만든 작은 합성 파일로 회귀 검사합니다. 운영 원문으로 공격하거나 워커 메모리를 실제로 소진하지 않습니다.

남은 제한: PDF·HWP 변환 전체의 프로세스별 CPU·메모리·시간 격리, 대량의 정상 병합 항목 등에 대한 누적 처리 예산은 별도 보완 대상입니다. 기존 HWP 하위 명령에는 timeout이 있으나 전체 파서가 격리됐다는 뜻은 아닙니다. 수집기의 SSRF 공인 IP·DNS 고정·리다이렉트 검사는 기존 방어와 회귀 검사로 확인하며 새 결함 수정으로 세지 않습니다. AI에는 기존 원문 경계·근거 검증·자동 공개 검증이 있으나 프롬프트 인젝션을 완전히 차단한다는 보장은 하지 않습니다. 의미를 조작하는 악성 원문에 대한 오프라인 평가 세트와 공개 보류 기준을 추가 검토해야 합니다.
