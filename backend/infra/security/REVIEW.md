# 보안 검토 기록 — 2026-11-15

이 기록은 확인한 코드·운영 정책, 수정한 항목, 남은 검증을 구분합니다. 전체 시스템에 취약점이 없다는 보증이나 침해 사고 확인 결과가 아닙니다. 실제 사용자 토큰·데이터로 공격하지 않고 회귀 검사는 격리된 테스트 DB에서 수행합니다.

## 1. 로그아웃 뒤 회전 전 토큰으로 세션을 재발급할 수 있는 경로

발견 근거: 기존 `AuthTokenService.refresh()`는 회전 전 토큰을 30초 동안 허용하지만 `revoke()`는 전달된 토큰 한 개만 삭제했습니다. T0 → T1 회전 후 T1으로 로그아웃해도 T0가 남아 유예 시간에 다시 토큰을 받을 수 있었습니다. 공격자는 유효한 토큰 사본을 가지고 있어야 하며, 이것만으로 임의 계정에 로그인할 수 있다는 의미는 아닙니다.

변경: 로그인별 `family_id`를 두고 회전한 토큰과 동시 요청에서 파생된 토큰을 같은 계보로 연결합니다. 로그아웃은 해당 계보를 모두 삭제합니다. 사용자 행 잠금 후 토큰과 현재 시각을 다시 확인해 로그아웃과 재발급 사이의 경합을 직렬화합니다. 별도 로그인에서 발급한 토큰은 유지합니다.

검증: `SecurityIntegrationTest.logoutRevokesGraceTokenAndSiblingButKeepsAnotherLogin`과 `racingLogoutAndRefreshCannotLeaveARefreshSessionAlive`. `Security regression proof` 워크플로는 고정한 과거 커밋의 서비스 코드로 첫 검사가 정확히 **401을 기대했지만 200이 반환돼 실패**하는지 확인하고, 현재 코드로 두 검사가 통과하는지 확인합니다. 다른 컴파일·DB·네트워크 오류는 재현 성공으로 인정하지 않습니다. 증거는 `logout-security-proof` artifact의 XML·JSON에 보관합니다. 해당 CI가 성공하기 전에는 실 DB 재현 완료로 기록하지 않습니다.

운영 영향: 새 컬럼·인덱스 마이그레이션이 있습니다. 기존 미회전 토큰의 로그인은 유지하고, 계보를 복원할 수 없는 이전 버전의 회전된 토큰은 유예를 종료합니다. 스키마 변경 후 앱만 과거 버전으로 되돌리는 작업은 기존 배포 보호 장치에 따라 제한됩니다. access token 즉시 폐기와 탈취 토큰 재사용 감지·계보 전체 폐기는 별도 과제이며 이번 수정으로 구현했다고 주장하지 않습니다.

검사기는 실제 Gradle `runtimeClasspath`의 204개(API)·152개(notification) 아티팩트를 내보내고 OSV에 정확한 버전으로 조회합니다. Python은 세 잠금 파일의 공개 registry 패키지를 중복 제거해 검사합니다. 검토 시 패치 후 Maven·Python·pnpm 조회 결과는 발견 0건이었습니다. 이는 **조회한 DB·버전·시점에 한정**되며 OS 이미지·네이티브 라이브러리·새 미등록 취약점까지 안전하다는 뜻이 아닙니다. OSV의 GHSA와 PYSEC 별칭을 각각 다른 실제 취약점으로 세지 않습니다.

재발 방지: Java·Python·웹 CI에서 보안 조회 실패나 취약점 발견을 성공으로 처리하지 않습니다. 공급자 응답 누락·개별 오류·미처리 페이지도 실패시킵니다. 자동 DB가 공식 권고보다 늦을 수 있어 검토한 프레임워크 최소 패치 기준도 검사합니다. Dependabot의 주간 업데이트 PR은 dev로 보내고 자동 병합하지 않습니다.

## 3. 개인 데이터 접근 권한

신청 준비함은 기존에도 사용자 ID를 사용해 소유권을 검사합니다. 기존 조회·상태 변경 검사에 HTTP 체크리스트 수정·삭제, 준비함 삭제, 다른 준비함의 작업 ID 혼합 검사를 보강했습니다. 요청이 거부되는 것과 함께 원래 소유자의 데이터가 바뀌지 않는지도 확인합니다. 기존 푸시 구독의 다른 사용자 기기 삭제 방지, 관리자 권한 회수 후 동일 JWT 거부 검사도 유지합니다. 취약점이 재현되지 않은 경로를 새로 발견·수정한 결함으로 표현하지 않습니다.

## 4. S3와 운영 권한 경계

운영 조회에서 이미 확인한 조치: 버킷의 공개 접근 차단 4개, 공개 ACL 부재, 비공개 정책 상태, 기본 암호화, 앱 IAM의 배포 경로 명시적 거부. 서버 방화벽의 전체 인터넷 공개 TCP 포트는 HTTP·HTTPS였으며 SSH 전체 공개는 확인되지 않았습니다.

이번 보완: 버킷에 명시적 HTTPS 강제 정책을 추가하고, 새 운영 보고·알림 중복 방지 경로를 앱 IAM에서 명시적으로 거부했습니다. 기존 배포 경로 거부도 유지합니다. AWS 서비스가 호출할 때 일부 네트워크 문맥이 생략되는 점을 고려해 서비스 주체는 전송 조건의 예외로 둡니다. 공개 접근 허용이나 새 자격 증명 생성, 데이터·백업 삭제는 하지 않습니다.

적용 후 IAM 시뮬레이션: 앱 주체의 원문·백업 Get/Put은 기존대로 허용되고, 배포·운영 경로 Get/Put은 명시적 거부였습니다. 예전에도 차단된 배포 경로를 이번에 처음 차단했다고 기록하지 않습니다. 앱과 백업의 자격 증명을 더 세분화하는 일은 후속 과제로 남습니다. 서명 URL은 이번에 추가하지 않았고, 공고 PDF는 기존 공개 상태·파일 경로 검증 후 서버 스트리밍 구조를 유지합니다.

## 5. 후속 검토 항목

- Vercel → Nginx에서 실제 사용자 IP를 신뢰할 조건과 요청 제한 키 검증. 전달 헤더를 무조건 신뢰하도록 바꾸지 않습니다.
- 인증 쿠키 경로의 CORS·Origin·SameSite 조건을 실제 브라우저로 검증. 현재 CORS가 차단하는 요청을 CSRF 취약점으로 단정하지 않습니다.
- CSP는 지도·로그인·PDF·서비스 워커의 출처 목록과 보고 방식부터 설계합니다. 정책을 무조건 강제해 기능이 깨지게 하지 않습니다.
- 수집기의 사설 IP·DNS 고정·리다이렉트 차단과 푸시 도메인 허용 목록은 기존 방어입니다. 우회 사례·회귀 검사를 추가 검토합니다.
- 외부 문서 파서의 크기·시간·메모리 제한, AI 프롬프트 인젝션과 공개 승인 경계, 컨테이너 이미지·배포 작업의 공급망, Git 과거 이력의 비밀값을 별도 점검합니다.
- AWS 관리자의 root 로그인 사용을 줄이고 별도 관리자 역할·MFA 체계를 정하는 작업은 운영자 설정을 동반합니다.
