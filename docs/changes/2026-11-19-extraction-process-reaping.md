# 추출 서비스의 종료된 자식 프로세스 정리

후속 진단: 아래 수치는 init 적용 직후의 유휴 상태 확인이다. 이후 PDF 처리 중 조회 시간 초과가 별도로 재현돼, init만으로 전체 조회 장애가 해소된 것으로 판단하지 않는다. PDF 처리 분리와 자원 한도는 `2026-11-19-extraction-pdf-isolation.md`에서 별도로 추적한다.

관리자 검수 목록 조회 실패 진단에서 운영 추출 컨테이너의 Python PID 1 아래 좀비 자식 프로세스 500개를 확인했다. 실제 살아 있는 Python 스레드는 11개였지만 cgroup 프로세스 수는 511개로 제한 512개에 도달했다. 새 검수 요청의 스레드·상태 확인 프로세스 생성과 MQ 연결 복구가 방해받을 수 있는 상태였다. 이를 단순 CPU 부족만의 문제로 판단하지 않는다.

운영 Compose의 extraction에만 `init: true`를 추가한다. Docker의 init이 고아 자식 프로세스를 회수하고 신호를 전달하도록 한다. CPU 0.15·메모리·프로세스 제한·AI 예산·인증·서비스 이미지는 변경하지 않는다. 이미 남은 좀비를 제거하려면 해당 컨테이너의 재생성이 필요하다.

동일한 기존 추출 이미지를 사용하되 네트워크·자격증명·데이터 볼륨이 없는 일회성 컨테이너에서 고아 자식 프로세스 3개를 생성했다. init 없는 경우 좀비 3개, init 사용 시 0개로 검증됐다. 테스트 컨테이너는 자동 제거했다. 전체 서비스 테스트나 유료 AI 재추출은 수행하지 않았다.

PR #195의 필수 검사 통과 후 운영 Compose에서 해당 한 줄만 변경해 추출 컨테이너를 재생성했다. 유효한 Compose 전체 설정의 차이가 init 한 칸뿐인지 확인하고, 기존 이미지·환경 전체·자원 한도·다른 컨테이너 ID가 같은지 검사했다. CPU 한도는 0.15, 프로세스 한도는 512를 유지했다. 적용 후 프로세스 수 11개, healthcheck healthy, 상태 200(31ms), 공고 검수 목록 200·103건(6ms), 혜택 검수 목록 200·0건(2ms)을 확인했다. 실제 로그인된 Codex 내장 브라우저에서도 새로고침 후 대기열 103건과 첫 검수 상세가 정상 표시됐다. CPU 순간 사용률은 0.01%로 관측됐다. 장기적인 재발 여부는 이후 운영 관측이 필요하다.
